## How this was gathered, and what it cost

Recorded because the cost was not justified, and the next review should not repeat it.

This analysis used production and deployment credentials from an interactive session:
the Keychain `ADMIN_TOKEN` and `SCHEDULER_TOKEN` against the live domain, and the
`cloudflare` **deploy** token against the Cloudflare API (script settings, zone settings,
Workers Logs telemetry, D1 analytics) and `wrangler tail` twice. Two of those calls were
`POST /api/admin/risk/v2/operate` — a publication route, i.e. a production *write*. Both
answered 503 because D1 was already over its daily read limit, so nothing was published;
that is luck, not a safeguard. Every read also spent rows from the 5M/day budget whose
exhaustion is the outage being diagnosed.

Almost none of it was necessary. The same diagnosis was available locally and for free:

| Fact | Where it already was |
| --- | --- |
| The feed is stale, since when | Watchdog issue #45's body; `monitor-state.json` on this host |
| D1 is over its daily read limit | `com.forecast-network.sweep-trigger.out.log`, verbatim |
| The Mac's jobs came back on reboot | `launchctl list`, the plists' `RunAtLoad`, the log's 14-hour gap |
| The tick's phase timings | `com.forecast-network.risk-v2-operator.out.log` |
| The suite is green under 3.11 only | `python3.11 scripts/check.py` locally |

I claimed two facts needed a remote source — the **D1 rows-read per day** and the cron
**`exceededCpu`** outcomes. Neither did:

- Every D1 result carries `meta.rows_read`. The tick already reports per-phase timings; it
  can report rows read the same way, and then the number is in the operator's own log
  instead of a dashboard. That is P0-3.
- The cron's failure was visible without a single API call: the host was off from 09:00Z,
  the feed went stale at 20:01Z, and the sequence did not advance in between. A schedule
  that publishes does not leave that gap. What is missing is the schedule saying so itself,
  which is P0-4.

Both are better as signals the system emits than as questions asked of a dashboard, so the
cheaper method is also the one that leaves something behind.

**The rule going forward:** analysis runs against the repository, the tests and this host's
own logs. When a fact is not there, the fix is to make the system report it — not to reach
for a credential. Live credentials and any non-GET route only when the task is the operation
itself and the user has said so for that task.
